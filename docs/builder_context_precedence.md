# Builder and Planning Context Precedence

v0.13.2 makes the stored Character Builder scratchpad part of the normal full-character generation pipeline and defines how it interacts with the concept and private Interview / Q&A.

## Why precedence is needed

Character Card Forge can now have several sources describing the same character:

- the main Generation Concept;
- manually entered Interview / Q&A answers;
- Character Builder fields;
- AI-inferred private interview answers;
- existing card fields included for regeneration;
- shared project, series, relationship, and attachment context.

Without explicit precedence, a model can resolve a conflict differently between the interview, full generation, and semantic repair passes. v0.13.2 gives the character-writing pipeline a stable order for character-specific planning sources.

## Character-specific planning order

When two character-specific planning sources disagree, use this priority:

1. **Source Generation Concept** — explicit facts supplied in the concept are the highest-priority character-specific source.
2. **Manual Interview / Q&A answers** — deliberate answers entered by the user are authoritative planning detail unless they contradict an explicit concept fact.
3. **Character Builder guidance** — non-empty Builder fields are deliberate structured planning guidance and outrank AI-inferred interview details and generic assumptions.
4. **AI-inferred interview answers** — useful connective planning, but allowed to fill gaps rather than replace higher-priority sources.
5. **Existing card values and generic inference** — useful when compatible, but they must not override the sources above.

Shared project context, series bibles, established relationships, and enabled attachments remain continuity constraints in their existing workflows. This precedence list is specifically about resolving character-specific concept/planning conflicts; it does not authorize a character to violate explicit project-wide canon.

When two high-priority sources appear inconsistent, generation should preserve the source concept and prefer the more specific directly stated detail rather than silently rewriting unrelated facts.

## Builder participation in Generate Character

The Character Builder remains a scratchpad and planning tool. v0.13.2 changes what happens to its **current stored non-empty values**:

```text
Builder scratchpad
      ↓
private interview planning
      ↓
full character generation
      ↓
semantic completeness repair, if needed
```

The Builder context is rendered from the existing Builder schema and grouped by Builder step. Blank fields do not consume prompt space.

Builder values are sent into:

- the initial private interview so inferred answers can respect deliberate Builder decisions;
- missing-answer retries;
- the full-character generation request;
- the bounded semantic repair pass.

This closes an important parity gap where a repair request could previously fix a missing field while forgetting the planning information used to create the original response.

## Manual versus AI-assisted Builder content

Builder AI fill and concept extraction still write only into the Builder scratchpad first. The user can review and edit that scratchpad before continuing.

v0.13.2 does **not** yet store per-field provenance saying whether each Builder value was typed manually, supplied by a preset, extracted from the concept, or generated by Builder AI. The current stored Builder state is therefore treated as the accepted planning scratchpad when Generate Character is launched.

Per-field provenance can be added later if a workflow needs finer precedence inside the Builder itself without changing this overall planning model.

## Planning context versus direct application

Using Builder state during **Generate Character** does not directly copy Builder fields into Character Card fields. It influences the generation request, whose result still goes through semantic validation and Generation Preview.

**Apply to Character** remains the explicit direct-projection action. In other words, Builder state can now guide normal generation even when the user has not first projected the scratchpad directly into Description, Personality, Scenario, name, tags, or Concept.

## Description projection correction

The older Builder implementation predated the v0.13 Description semantics and projected role, backstory, skills, secrets, and behavioural boundaries into Character Card Description.

That is no longer valid. Description is physical/external presentation.

v0.13.2 changes direct Builder projection to:

```text
Description
└── Appearance
```

Identity/history/behavioural Builder material instead folds into the Personality/lore-side projection:

```text
Personality / lore-side content
├── Role / archetype
├── Goals
├── Core traits
├── Strengths
├── Flaws
├── Motivations
├── Fears / vulnerabilities
├── Speech style
├── Mannerisms
├── Relationship style
├── Backstory
├── Skills / capabilities
├── Secrets / hidden complications
└── Behavioural boundaries
```

Scenario continues to receive setting/opening information from the Scene Builder.

This makes direct Builder application consistent with the Default template and full-generation rule that Character Card Description is for visible physical appearance rather than a general biography container.

## Semantic repair

The v0.13 semantic repair pass now receives the planning sources needed to preserve the original intent while filling missing required content:

- source concept already supplied by the parent repair service;
- manual Interview / Q&A answers;
- Builder guidance;
- lower-priority AI interview notes.

The repair request is reminded to alter only what is needed for completeness and not rewrite unrelated established facts.

## Metadata and privacy

The completed generation metadata records a compact diagnostic summary of Builder participation:

- whether Builder context was used;
- number of non-empty Builder fields;
- number of populated Builder steps;
- the planning precedence version/order.

The raw Builder scratchpad is **not duplicated into completion metadata**. It remains ordinary project workspace data.

AI-generated private interview answers remain ephemeral as before.

## Compatibility

No project-format or template-format bump is required for v0.13.2.

Existing Builder state is already stored under the character workspace, so older projects automatically benefit when their Builder contains non-empty values. Projects with an empty Builder behave as before apart from the corrected direct Description projection when Builder data is later applied.
